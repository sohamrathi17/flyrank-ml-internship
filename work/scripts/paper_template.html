Which Pages Should You Refresh First?

A month-ahead review queue for search visibility decline, tested on ~50,000 pages of real Search Console data against a transparent rule.

Soham Rathi · October 2026 · Code and notebooks

Abstract/Problem/Data/Method/Results/Limitations/Recommendations/Reproducibility/Credit

Abstract

Content editors have time to review only a handful of a site's pages each month, so I asked which pages should be at the top of that list if the goal is to catch the ones that will keep losing search visibility next month. Using the FlyRank ML Internship warehouse, about 79 million rows of pseudonymised daily Google Search Console data, I built monthly snapshots in which features come from one month and the outcome (daily impressions falling more than 20%) from the next. I compared a transparent rule ("how much has this page already slid within the month?") with logistic regression and gradient-boosted trees on 16 signals, using client-grouped cross-validation, a time-aware split, a sealed final month evaluated once, and a client-level bootstrap. The rule put about 71-72% true decliners in each client's top 20, against a base rate near 49%, and held that level on the sealed month. The learned models traded small gains on one metric for losses on the other, and the best combined score was about one point above the rule, within the bootstrap noise. The result is a decision-support queue with reason codes, actions and confidence labels for choosing which pages to review first, not a causal claim about what a refresh will achieve.

1Introduction: the decision this supports

Picture an editor responsible for a client site with 567 tracked pages, the median in this data. Each month they have time to open perhaps 20. Some pages are quietly sliding in Google's results; reviewing those early (refreshing facts, tightening titles, adding depth) is the cheapest moment to act. Reviewing a healthy page is wasted time, and sometimes worse than doing nothing.

So the question is not "will this page decline?" for one page. It is a ranking question with a budget: which 20 pages first? That framing decides everything that follows. The metric is precision@20 per client (of the 20 pages at the top of a client's list, how many really declined next month), with a second check on how much of next month's lost visibility those 20 pages hold. Both were fixed before any model was trained.

The obvious shortcuts do not work well. In a first look at the starter data, "biggest pages first" caught a lot of the lost traffic but was less accurate than random order, and "oldest" or "least recently updated" barely beat random. In the warehouse slice used here, "biggest pages first" reached a precision@20 of 0.43 against a base rate of 0.49.

What I excluded, and why.

  • Everything from the label month as an input: it is the answer.
  • "Last updated" and "last optimised" dates: the content table is a snapshot built after the panel ended, and for 78% of pages the "last updated" date falls after the decision moment. Using it would leak the future.
  • GA4 engagement data: available on only about 4% of daily rows in the development month.
  • IDs as features: client and page IDs are pseudonymous hashes used only to group, split and join. No client names, domains, URLs or search queries appear anywhere in this work.

3Methodology

Label

A page is declining when its average daily impressions next month are more than 20% below this month's. This is an observed outcome measured one month after the decision moment, not a rule someone defined on the same data. In the development month (March → April) 47% of slice pages declined; the rate moved a lot between months (21% for February → March, 59% for May → June).

Baseline rule

Before building it, I checked two signals the rule would lean on, each with a bucket table and sample sizes. Both were confirmed:

  • Momentum within the month (late-half vs early-half daily impressions): the steeper the slide, the more often the page kept declining (Figure 2).
  • CTR versus position (the signal behind FlyRank's CTR-fix logic): pages with clicks but CTR below their position tier's median declined more often, from 63% (under half the tier median) down to 34% (more than twice it).

The rule: score = impressions per day lost between the first and second half of the month, multiplied by 1.5 when CTR is below its position-tier median. It is frozen and is what every model must beat.

Model

Logistic regression on 16 features, all knowable at the decision moment: impressions, clicks, CTR, impression-weighted position, momentum, size of the within-month drop, days with impressions, daily volatility, position change, share of the month on the single biggest day, page age, and keyword metadata (search volume, competition, keyword length, content type, intent). The ranking score is the model's decline probability × (1 + within-month drop per day). Gradient-boosted trees (classifier and expected-loss regressor) were also tested.

Validation design

  • Grouped by client: 5-fold cross-validation where each fold holds out whole clients, so every page is scored by a model that never saw its site.
  • Time-aware: train on February → March, test on March → April.
  • Sealed final month: the recipe was frozen, trained on April → May, and evaluated once on May → June. The receipt was written by that single run.
  • Uncertainty: a bootstrap that resamples clients (2,000 times) for the model-minus-rule difference.

Leakage checks

  • Adding next-month impressions as a deliberate leak pushed ROC-AUC to 0.999; removing it brought the honest value back to 0.63. The test harness catches leaks.
  • A random (non-grouped) split inflated ROC-AUC to 0.72: about 9 points come from recognising a site already seen, which a new client would not get.
  • No label column or post-decision snapshot date is a feature. Dropping all keyword metadata changed results by less than one point.
  • Disclosed choice: the slice requires full Search Console coverage in the label month, which drops 18.5% of otherwise eligible pages.

4Results

Headline: the transparent rule lifts precision@20 from about 0.49 to about 0.71 and held up on a sealed month. The learned models were not measurably better than the rule.

How sure are these differences?

Difference (mean over clients)Development (22 clients)Sealed month (28 clients)

The intervals for "model minus rule" on precision include zero in both periods, and on the sealed month the rule caught slightly more of the lost impressions. The rule's lift over the base rate is large and clearly above zero in both. Honest reading: the rule is the result; the model confirms it rather than improving on it.

The model is still useful as an explanation. Its largest weights push toward "decline" for a large within-month drop, high impressions and a single-day spike, and toward "holds up" for clicks and momentum. High impressions with few clicks behaves like a CTR warning, consistent with the signal check above.

Probabilities do not transfer between months. A model trained on February → March (21% declined) predicted on average 24% for March → April, where 47% actually declined. Its ranking held up; its probabilities did not. The queue therefore shows ranks and reasons, never "X% chance".

5Limitations and honest framing

  • Observational, not causal. This work observed which pages kept losing visibility; it did not test what a refresh does. Nothing here says reviewing or refreshing a page will reverse a decline.
  • Not a model of Google. It describes patterns in one portfolio's data over a few months of 2026.
  • Few, unequal clients. Only 22-28 clients have 20 or more pages in a month, the three largest hold about two thirds of the pages, and only 8 clients were entirely new to the time-aware model. For clients with fewer than ~100 pages the queue showed no lift.
  • Population filter uses the outcome month. Pages without full Search Console coverage next month are dropped; pages that vanished were never scored.
  • One label definition (a 20% month-over-month drop). Seasonality and falling demand look the same as a page-level problem.
  • Most common false alarm: a short spike early in the month that fades and then returns to normal. The rule reads that as a slide.

6Ranked recommendations: the action playbook

Each month, for each client, the queue lists pages in score order with an action, up to two reason codes and a confidence label. Built on 31 March from a model trained on February → March and graded afterwards on April:

  1. Start with the top 10-20 of each client's queue, high-confidence rows first.
  2. Refresh sliding page-one pages (late-month impressions under 80% of early-month, average position ≤ 10): update facts, examples, title and description.
  3. Expand sliding pages in positions 11-20: add missing subtopics and depth.
  4. Monitor slides that look like a fading one-day spike or sit deeper than position 20. Monitor pages decline about as often as the others; the label means the right action is unclear, not that the page is safe.
  5. Protect steady page-one pages: listed so nobody "fixes" what works.
  6. Before any edit, check daily impressions in Search Console for a spike, a seasonal topic or a tracking gap.
  7. Do not use the queue for clients under ~100 pages, and never show it as a forecast or use it to automate rewrites, redirects or deletions.
  8. Re-check every month: if precision@20 falls below the plain rule for two months, use the rule.

7Reproducibility

Everything is in the public repository sohamrathi17/flyrank-ml-internship. Each step is a notebook that runs top to bottom:

  • Data contract: grain, counts, availability, five features, the deliberate leak.
  • Baseline rule: two signal checks, the rule, a hand review of the top 10.
  • Models vs baseline: grouped cross-validation and error analysis.
  • Validation and leakage audit: random vs grouped vs time-aware splits.
  • Action playbook: the queue, human review, monitoring triggers.
  • Capstone: sealed month, bootstrap, and the build of this page.

Shared code lives in work/scripts/lane_data.py (slice builder, rule, models, metrics) and work/scripts/sealed_test.py. Every number on this page is read from the committed JSON receipts in work/outputs/ by work/scripts/build_paper.py. Seed 42 throughout; scikit-learn 1.6.1. To rerun: request access to the dataset, log in with a read token (hf auth login), pip install -r requirements.txt duckdb, and run the notebooks in order.
